# Лаборатори №5 — REST API-ийн тест дизайн

## 1. Оюутны мэдээлэл

- **Оюутан:** Ц.Бэлгүтэй
- **Оюутны код:** B232270053
- **Систем:** Хичээлд бүртгүүлэх REST API
- **API хаяг:** `http://localhost:3000`
- **Тестийн хэрэгсэл:** Postman Collection, Newman CLI

## 2. Орчны мэдээлэл

| Үзүүлэлт | Хувилбар / утга |
|---|---|
| Node.js | v26.5.0 |
| npm | 11.17.0 |
| Newman | 6.2.1 |
| API порт | 3000 |

API нь Node.js-ийн `http` модулийг ашиглан ажиллана. Туршилтын өгөгдөл нь серверийн санах ойд хадгалагддаг тул серверийг дахин эхлүүлэхэд өгөгдөл шинээр үүснэ.

## 3. Тест дизайны таван алхам

### Алхам 1. Бие даан тестлэгдэх функцийг тодорхойлох

Энэ лабораторид хичээлд бүртгүүлэх үйлдэл болон түүнтэй холбоотой өгөгдөл, нөхцөлүүдийг шалгав.

| № | Функц | Тестлэх зорилго |
|---|---|---|
| F01 | Оюутан үүсгэх | Оюутны төлөв болон үзсэн хичээлүүдийг хадгалах |
| F02 | Хичээл үүсгэх | Хичээлийн урьдчилсан нөхцөлийг хадгалах |
| F03 | Хичээл авах | Хичээл болон түүний урьдчилсан нөхцөлийг шалгах |
| F04 | Бүртгэл үүсгэх | Оюутан, төлөв, хичээл, урьдчилсан нөхцөл болон хүсэлтийн өгөгдлийг шалгах |
| F05 | Бүртгэлийн жагсаалт авах | Бүртгэлүүдийн жагсаалтыг буцаах |

### Алхам 2. Сонголтууд ба эквивалент ангиллууд

| Шалгах үзүүлэлт | Сонголт / ангилал |
|---|---|
| Оюутан | Бүртгэлтэй / бүртгэлгүй |
| Оюутны төлөв | `active` / `inactive` |
| Хичээл | Байгаа / байхгүй |
| Урьдчилсан нөхцөл | Хангасан / хангаагүй |
| `studentID` | Өгөгдсөн / дутуу |
| `courseID` | Өгөгдсөн / дутуу |
| Хичээлийн урьдчилсан нөхцөл | Байгаа / байхгүй |
| `coursesTaken` | Шаардлагатай хичээлийг агуулсан / хоосон |
| JSON хүсэлтийн өгөгдөл | Зөв форматтай / буруу форматтай |
| Давхар алдааны нөхцөл | Идэвхгүй оюутан болон байхгүй хичээл зэрэг тохиолдох |

### Алхам 3. Төлөөлөх утгууд сонгох

| Ангилал | Төлөөлөх утга |
|---|---|
| Идэвхтэй оюутан | `STU_TC01`, төлөв `active` |
| Идэвхгүй оюутан | `STU_TC03`, төлөв `inactive` |
| Байгаа хичээл | `COURSE_TC01` |
| Байхгүй хичээл | `COURSE_MISSING_TC04` |
| Хангасан урьдчилсан нөхцөл | `coursesTaken: ["CS201"]` |
| Хангаагүй урьдчилсан нөхцөл | `coursesTaken: []` |
| Урьдчилсан нөхцөлтэй хичээл | `prerequisites: ["CS201"]` |
| Урьдчилсан нөхцөлгүй хичээл | `prerequisites: []` |
| Дутуу `studentID` | `{ "courseID": "COURSE_TC06" }` |
| Дутуу `courseID` | `{ "studentID": "STU_TC07" }` |
| Буруу JSON | `{"studentID":` |

Тест бүрт ялгаатай ID ашигласан нь нэг тестийн өгөгдөл нөгөө тестийн үр дүнд нөлөөлөх эрсдэлийг бууруулна.

### Алхам 4. Тестийн спецификаци тодорхойлох

| TC | Нөхцөл | Хүлээгдэж буй HTTP статус | Хүлээгдэж буй үр дүн |
|---|---|---:|---|
| TC01 | Идэвхтэй оюутан шаардлага хангасан хичээлд бүртгүүлэх | 201 | `result: OK`, `registrationID` тоон утгатай |
| TC02 | Бүртгэлгүй оюутан | 200 | `ERROR_NO_STUDENT` |
| TC03 | Идэвхгүй оюутан | 200 | `ERROR_INACTIVE_STUDENT` |
| TC04 | Байхгүй хичээл | 200 | `ERROR_NO_COURSE` |
| TC05 | Урьдчилсан нөхцөл хангаагүй | 200 | `ERROR_PREREQUISITES`, `missing` дотор `CS201` |
| TC06 | `studentID` дутуу | 400 | `ERROR_BAD_REQUEST` |
| TC07 | `courseID` дутуу | 400 | `ERROR_BAD_REQUEST` |
| TC08 | Урьдчилсан нөхцөлгүй хичээлд бүртгүүлэх | 201 | `result: OK`, `registrationID` тоон утгатай |
| TC09 | `coursesTaken` хоосон, харин урьдчилсан нөхцөл шаардлагатай | 200 | `ERROR_PREREQUISITES`, `missing` дотор `CS201` |
| TC10 | Оюутан идэвхгүй бөгөөд хичээл байхгүй | 200 | `ERROR_INACTIVE_STUDENT` |
| TC11 | Буруу форматтай JSON | 400 | `ERROR_BAD_JSON` |

**Тэмдэглэл:** Бизнесийн алдааны нөхцөлүүдэд сервер HTTP 200 буцааж, алдааны төрлийг `result` талбарт илэрхийлдэг. Харин дутуу шаардлагатай талбар болон буруу JSON-д HTTP 400 ашигладаг.

### Алхам 5. Бодит тест кейс хэрэгжүүлэх

Тестүүдийг `lab05-collection.json` Postman Collection-д хэрэгжүүлж, Newman CLI ашиглан ажиллуулав. Нийт 11 тест кейс, тест бүрд 3 HTTP хүсэлт буюу нийт 33 хүсэлт ажиллана. Хүсэлтүүдийн дүнд HTTP статус, `result` талбар, шаардлагатай үед `registrationID` болон `missing` жагсаалтыг шалгах assertions ашигласан.

| Файл | Зориулалт |
|---|---|
| `server.js` | Өгөгдсөн REST API сервер |
| `lab05-collection.json` | Хэвийн, PASS тестийн багц |
| `lab05-collection-fail.json` | Санаатай буруу хүлээлттэй FAIL багц |
| `results/newman-pass.txt` | PASS ажиллуулалтын бүрэн гаралт |
| `results/newman-fail.txt` | FAIL ажиллуулалтын бүрэн гаралт |
| `results/newman-down.txt` | Сервер зогссон үеийн бүрэн гаралт |

## 4. Туршилтын үр дүн

### 4.1 Үр дүнгийн хураангуй

| Үзүүлэлт | PASS | FAIL | DOWN |
|---|---:|---:|---:|
| Хүсэлт ажиллуулсан | 33 | 33 | 33 |
| Assertions ажиллуулсан | 26 | 26 | 26 |
| Амжилтгүй хүсэлт | 0 | 0 | 33 |
| Амжилтгүй assertion | 0 | 1 | 26 |
| Newman exit code | 0 | 1 | 1 |

### 4.2 PASS туршилт

`lab05-collection.json` багцыг сервер ажиллаж байх үед ажиллуулахад 33 хүсэлт амжилттай боловсруулагдаж, 26 assertion бүгд тэнцсэн. Newman-ийн exit code `0` байсан нь шалгалтууд хүлээгдсэн үр дүнтэй таарсныг илтгэнэ.

### 4.3 FAIL туршилт

`lab05-collection-fail.json` багцад TC01-ийн хүлээгдэж буй HTTP статусыг зориудаар `201` биш `200` болгон өөрчилсөн. API бодитоор `201` буцаасан тул нэг assertion амжилтгүй болж, Newman-ийн exit code `1` болсон. Энэ нь тестийн хүлээлт бодит үр дүнтэй зөрөх үед алдааг илрүүлж чаддагийг харуулна.

### 4.4 DOWN туршилт

Серверийг зогсоосны дараа `lab05-collection.json` багцыг дахин ажиллуулахад `ECONNREFUSED 127.0.0.1:3000` алдаа гарсан. Нийт 33 хүсэлт холбогдож чадаагүй бөгөөд хариу байхгүйгээс 26 assertion амжилтгүй болсон. Newman-ийн exit code `1` байв. Энэ үр дүн нь бизнес логикийн алдаа бус, API серверт холбогдох боломжгүй байсныг илтгэнэ.

Бүрэн гаралтыг `results/` хавтас дахь гурван текст файлаас шалгаж болно.

## 5. Дүгнэлт

Энэ лабораторийн хүрээнд хичээлд бүртгүүлэх REST API-д тест дизайны таван алхмыг хэрэгжүүллээ. Эхлээд бие даан тестлэгдэх функцуудыг тодорхойлж, тэдгээрийн боломжит нөхцөлүүдийг эквивалент ангилалд хуваасан. Дараа нь ангилал бүрийг төлөөлөх утгууд сонгон, хүлээгдэж буй HTTP статус болон үр дүнг тодорхойлов. Эдгээр спецификацид үндэслэн 11 тест кейс бүхий Postman Collection бүтээсэн. Newman ашиглан нийт 33 хүсэлт, 26 assertion ажиллуулж, хэвийн нөхцөлд бүх шалгалт тэнцсэнийг баталгаажуулсан. Санаатай буруу хүлээлт оруулсан FAIL тест нэг assertion-ийн зөрүүг илрүүлсэн. Серверийг зогсоосон DOWN туршилтаар холболтын алдаа болон assertion-ийн алдааг ялгаж ажигласан. Туршилтын үр дүнг гурван тусдаа файлд хадгалсан тул дараа нь дахин шалгах боломжтой. Энэ ажлаар тест кейсийг зөвхөн амжилттай хувилбараар хязгаарлахгүй, буруу оролт болон системийн хүртээмжгүй нөхцөлийг хамруулах шаардлагатайг ойлгосон.
